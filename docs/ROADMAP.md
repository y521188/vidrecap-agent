# 开发计划（路线图）

> 本文件是**规则层**资产，描述接下来几次提交的目标、产出、验收标准与"不做什么"。
> 分层规矩见 [AGENTS.md](../AGENTS.md)，架构讲解见 [ARCHITECTURE.md](ARCHITECTURE.md)。

## 总原则

1. **考卷先行**：先定义"什么算好句子"的评测集，再写实现——标准先立，实现围绕标准写。
2. **每次提交自带验收**：不写"以后再补测试"，测试与实现同一次提交落地。
3. **行为不变的重构要有证据**：不改变行为的提交，必须证明 `vidrecap demo` 输出与改前逐字节一致。
4. **骨架已就位**：函数签名与契约已写好，后续提交只填实现、补测试，不再改结构。

## 依赖关系

```
提交1（打分器）──→ 提交2（考卷+跑分）──┐
        │                              ├──→ 提交4（注毒+端到端）
        └────────→ 提交3（语义修正）────┘
```

提交 2 与 3 都依赖提交 1，彼此独立，可以调换顺序；提交 4 依赖 3。

## 提交 1：规则层三指标打分器 ✅ 已完成

**目标**：能对一句话给出可解释的质量分——这是后续"低于阈值就修"的判据。

**产出文件**

| 文件 | 动作 |
|---|---|
| `vidrecap/rules/quality.py` | 已实现：三指标规则 + 加权总分 + 扣分原因 + 达标判定 |
| `vidrecap/rules/api/__init__.py` | 已挂出 `HeuristicScorer` / `is_acceptable` / `unacceptable_reason` / `SEVERE_METRIC_FLOOR` |
| `tests/test_quality.py` | 新建 34 个测试：三指标正反例、加权公式、确定性、闸门、插座形状 |

**三指标规则**（每条扣分都写进 `reasons`，可以直接讲给业务方听）

| 指标 | 规则 | 扣分 |
|---|---|---|
| 清晰度 | 句首直接是谓语（"介绍了…"）→ 缺主语 | −0.60 |
| | 指代词过密（他/这个/那个；"其他"这类词不算） | 按比例，最多 −0.55 |
| 通顺度 | 相邻两字词重复（"介绍介绍了"） | −0.60 |
| | 虚词重复（了了、的的） | −0.40 |
| | 标点连用 | −0.30 |
| | 长句中间没有停顿标点（连读） | −0.25 |
| | 句子过短（< 6 字）/ 过长（> 80 字） | −0.25 / −0.20 |
| 完整度 | 结尾没有终止标点（被截断） | −0.55 |
| | 以停顿标点结尾（话说一半） | −0.55 |
| | 看不出谓语（结构不成型） | −0.30 |

**闸门：实现时发现的关键设计。** 只用"加权总分 ≥ 阈值"是不够的——实测发现
缺主语（总分 0.70）、指代模糊（0.72）、词语重复（0.82）、截断（0.89）**光看总分全部过线**，
因为通顺度只占 0.3、完整度只占 0.2，单项全崩也拉不垮加权平均。
因此达标判定加了一条**一票否决**：任一指标低于 0.5（`SEVERE_METRIC_FLOOR`），整句判为需修正。
标准只写在规则层一处，规划层挑句子、评测算准确率都调它——线上判的与考卷量的是同一个标准。

**刻意不做**：完整度不查"是否覆盖原文全部信息"（概括本来就该丢细节，用覆盖率会误伤好句），
所以 `context` 参数在当前启发式实现里不参与打分；模型档实现会用它。
另有一个专门的测试锁住这条决定：换一个长短不同的原文，同一句话的分数必须完全相同。

**验收**：已完成。打分测试 34 个全绿；全库 147 个测试全绿；demo 输出与最初基准逐字节一致。
**不做什么**：不碰服务层、不改调度器、不做修正。

| `vidrecap/monitor/evals/runner.py` | 已实现：`run_scorer_eval` / `run_eval` / `baseline_checks` |

| `vidrecap/rules/baselines.py` | 按首次实测校准（0.75/0.90 → 0.95/0.95） |
| `tests/test_evals.py` | 新建 23 个测试：加载器、指标算法、成绩单、基线门槛、命令行 |
| `README.md` | 发榜：公布实测成绩与"考卷要打折扣看"的说明 |

**考卷配比**：清晰度 8 坏 + 4 好、通顺度 8 坏 + 4 好、完整度 8 坏 + 4 好、
混合 5 坏、好句对照 8 好，共 49 条。

**指标定义**

- **阈值准确率** = 判"过/不过"与标准答案一致条数 ÷ 总条数。
  判的依据是**规则层的达标判定**（阈值 + 单项一票否决），不是裸的总分过线——
  线上闸门用的就是这套判定，考卷必须量同一个东西。
- **排序正确率** = 所有（好句, 坏句）配对中"好句分更高"的比例，同分算半分；
- **分类别准确率** = 按 `category` 拆开的阈值准确率，看在哪类病句上翻车。

**首次实测（提交 2 完成时）**：49/49 全对，阈值准确率 100%、排序正确率 100%。
基线随之上调为 **0.95 / 0.95**——不设成满分，是因为门槛一旦等于满分，
规则的小改动一动就红，反而会诱导别人去改考卷而不是改实现。

**实现时的两点调整**

1. **规则分了两档**：硬缺陷（缺主语、指代过密、词重复、虚词重复、标点连用、
   被截断、话说一半、碎片、严重连读）各自扣分都超过 0.5，单独命中一条就足以
   判不合格；轻扣（稍长、略短、看不出谓语、轻度连读）只做辅助信号。
   依据是：三个指标加权平均、权重都小于 1，单条扣分不到 0.5 就等于没有闸门作用。
2. **基线对照挪进监控层**（`baseline_checks`）：命令行原先要直接引用规则层拿基线数值，
   这违反依赖方向；现在由监控层给出"哪条不达标"，用户层只负责打印。

**刻意不做**：不写修正器；不接真实模型（留给路线图）。

两个以上对不上才算越界。顺手把该题加长到 50 字以上，让它真正走到修正路径。

**已知局限**（文档写明，测试锁住）：同义改写（原文"缺席"、修正写"没到场"）

### 提交 7：失败重试与降级（服务层）✅ 已完成

**目标**：真实模型会超时、会限流，单个分片失败不能炸掉整个任务，也不能静默丢内容。

| 文件 | 动作 |
|---|---|
| `vidrecap/service/orchestrator.py` | LLM 调用包上指数退避重试（次数、初始等待可配，默认 3 次 × 0.5s 起）；重试耗尽按 `PipelineConfig` 新开关走：跳过该分片并记入 `RecapStats.failed_shards`（默认），或整体抛错 |
| `vidrecap/data/models.py` | `PipelineConfig` 加 `max_retries` / `retry_initial_delay` / `retry_backoff` / `on_shard_failure`（默认值只在这里声明一次）；`RecapStats` 加 `failed_shards` |
| `tests/test_orchestrator.py` | 扩充：假 LLM 前 N 次抛错再成功 → 重试后成功且调用次数正确；始终抛错 → 跳过 + 统计正确；策略为抛错模式 → 整体失败 |

重试手写约二十行，不引 tenacity（docs/REUSE.md 里有替换方案备着）。归属表里
"失败重试"明确写在服务层——它是执行关切，不进规划层。

**实现时的边界决定**：重试只包**分片摘要**这一处调用。压缩合并阶段（`compress`
里的 `summarize`）不加跳过——合并步骤没有"跳过一片"的语义，失败就整任务失败；
要给它加重试，等真实使用中那里真的开始失败再说（YAGNI）。

**验收**：已完成。新增 4 个测试、全库 225 个全绿；瞬时失败 1 次重试后成功
（调用次数断言）；持续失败默认跳过并计入 `failed_shards`、概括为空不崩；
`raise` 策略整任务失败；`max_retries=0` 时每片恰好调用一次；默认 demo 输出
逐字节一致。

| 文件 | 动作 |
|---|---|
| `vidrecap/data/store.py` | 新建：sqlite3（标准库）存分片结果；任务指纹 = 输入内容指纹，内容没变才能复用 |
| `vidrecap/data/api/__init__.py` | 挂出 `TaskStore` |
| `vidrecap/service/orchestrator.py` | 每片摘要落库；`--resume`（或参数）时先查库，已完成的分片直接复用，不重新调模型 |
| `vidrecap/user/cli.py` | `demo` 加 `--store 路径`（给了才启用持久化，默认关闭，保持零依赖开箱即用） |
| `tests/test_store.py` + `tests/test_orchestrator.py` 扩充 | 新建：假 LLM 第 3 片抛错 → 重跑 → 前 2 片调用计数为 0（没重新调模型）→ 最终输出与一次跑完一致；内容指纹变了必须全部重跑 |
| `AGENTS.md` | 文件清单同步 |

**实现时的两个设计决定**

1. **缓存是内容寻址的**：键 = 命名空间（模型/提示词）+ 分片原文哈希。原文改一个字
   或换个模型就整片重算；反过来，不同时长的源只要前几片逐字相同就直接命中
   （测试里 1.5h 的源复用了 1.0h 跑出的 5 片——这正是内容寻址的语义，不是巧合）。
2. 缓存存的是**质检之后的最终结果**（含平均分与修正数），命中后连打分器都不用跑。

**验收**：已完成。新增 4 个测试、全库 230 个全绿；中断（4 片失败）重跑只调 4 次
模型且结果与一次跑完一致；同输入重跑零调用；换命名空间全部重算；质检字段经
缓存往返无损；不传 `--store` 时行为与改前完全一致（默认 demo 输出逐字节一致）。

**实现时的两个设计决定**

1. **"频率过低"用相对占比（台词份额）而非绝对次数**：绝对次数对长视频不收敛
   （说了一小时的常驻嘉宾和说了十分钟的嘉宾都是"几百次"），占比才符合
   "配角"的直觉。默认阈值 0.05，大咖与无标签发言豁免，无档案源整体跳过策略。
2. **偏离说明**：策略考卷没用 monitor/evals 的 JSONL，直接写在

   与提交 4 砍掉 scenarios.py 同一条 YAGNI 理由。

**验收**：已完成。新增 7 个测试、全库 252 个全绿；边界（占比恰等于阈值）保留；
`vidrecap demo --catalog` 端到端跑通：群众演员（1 句）被过滤且不进任何摘要，
大咖发言保留，统计行可见；默认 demo 输出逐字节一致。

### 提交 11：skill-md 技能配置 + 双重提示词（用户层 + 数据层 + 外部层）✅ 已完成

- `data/models.py`：`SkillConfig`（system_prompt、summarize_instruction、质量参数、人物策略引用）
- 用户层（装配根）解析 skill-md：受限 frontmatter 格式，**不引 YAML 依赖**
- `LLMClient.summarize` 加可选 `system` 参数（默认空、向后兼容），两级约束分别成消息
- CLI 加 `--skill 文件.md`；优先级写死：命令行 > 技能文件 > 默认值

**实现时的两个关键决定**

1. **指令语义修正**：原先 `instruction` 被当成 system 消息发出（历史遗留）；现在
   `system` = 角色与规则，`instruction` = 本次要求，各成一条消息，正文最后。
   实测发现这会打挂"按老签名写的适配器"，于是加了**向后兼容**：system 为空时
   **根本不传该参数**——测试里那些只认 instruction 的假模型不用改一行就照跑，
   这正是客户自写适配器会遇到的场景。
2. 技能文件格式对齐 **Agent Skills 开放标准**（头部元数据 + 正文指令），
   解析只认受限平铺格式（缩进行续上一键），不引 PyYAML；示例见
   `skills/新闻摘要.md`。

**刻意不做**：压缩合并阶段不带 system 提示词（只包分片摘要）——要让全局概括也吃
系统提示词，得把配置传进 `compress`，等真实使用提出需求再加。

**验收**：已完成。新增 15 个测试、全库 267 个全绿；优先级三档（命令行 > 技能 > 默认）
逐项断言；双重提示词实测到达模型（记录式假模型 + 假 HTTP 服务三条消息）；
`vidrecap demo --skill skills/新闻摘要.md` 跑通；默认 demo 输出逐字节一致。

### 提交 12：画面与人物动作（外挂为主，成本敏感）✅ 已完成

- 外挂脚本扩展：抽帧（默认稀疏、场景切换加密、密度可配）→ 视觉模型产"谁在做什么"事件行
- 事件行与语音字幕按时间对齐，经 `MediaSource` 适配器进同一条流水线
- 合并阶段提示词升级：带人物线/剧情线约束的全局概括
- 按 帧 计费是主要成本，放在前三件跑顺真实视频之后再做

**实现方式与三处偏离**

1. **抽帧用 ffmpeg 固定间隔**（默认 120 秒、上限 200 帧，运行前打印帧数供估算），
   **场景切换加密未做**：没装 ffmpeg 的机器上场景检测没法验证，而固定间隔的
   成本一眼可估。PySceneDetect（BSD-3）已在 REUSE.md 备着，需要时再接。
2. **画面事件合进字幕轨**，不新建插座：视觉描述写成带 `〖画面〗` 前缀的字幕行，
   时间对齐后与语音行一起排序——分片、质检、人物策略、断点续跑全部照旧生效，
   零改动复用整条流水线。
3. **视觉能力挂在 OpenAI 适配器的 `describe_image` 方法上**（图片内联成 data URI），
   不为它单建插座——只有一个实现，按 YAGNI 不引入抽象。
4. **合并阶段的"剧情线"提示词升级未做**：与提交 11 的保留项同因（要把配置传进
   `compress`），等真实视频提出需求再加。

**验收**：已完成。全库 270 通过、1 跳过（抽帧测试需 ffmpeg，本机没有、
CI 的 Ubuntu 自带）；轨道合并、参数转发、看图消息组装均有断言；
默认 demo 输出逐字节一致。

把引擎从"一次性命令行"变成"常驻服务"：调用方 POST 一个摘要请求，进度边跑边推，
跑完返回结果。

| 文件 | 动作 |

| `vidrecap/user/assembly.py` | 新建：适配器选型从 cli 提炼出来，命令与服务端共用一份（两处各写一份迟早会漂） |
| `vidrecap/user/api/__init__.py` | 挂出服务入口 |
| `vidrecap/user/cli.py` | 新增 `serve` 子命令；改用 assembly 的装配函数 |
| `tests/test_server.py` | 新建：真起服务、逐行读事件流、404/400/429 路径 |

**为什么先不上 gRPC**：服务化的价值在"常驻、被调用、推进度"这个形态，不在协议。
零依赖的 HTTP + SSE 就能把形态做完整；等有了明确的 gRPC 生态对接方，
再按"加依赖先问"换实现——接口契约到那时已经稳定，换实现是局部改动。

**三条有意为之的边界**

1. **默认只绑 127.0.0.1**：外壳不含鉴权，对外暴露请自行加反向代理与鉴权；
2. **同时最多 2 个任务**（超了回 429，不排队）：防止一次涌进来的请求把机器打满；
3. **请求模型逐字段校验**（负时长、拼错字段名一律回 400）：服务是信任边界，
   坏参数不许进流水线。

**验收**：已完成。全库 278 通过、1 跳过；真机探针：命令行起服务 → 外部客户端调用 →
拿到 2 次进度事件 + 结果（`--catalog` 下配角被过滤的效果在结果里可见）；
默认 demo 输出逐字节一致。
